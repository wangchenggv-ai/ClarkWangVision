# 重复记录根因分析

> 2026-05-22 | 生产 Bitable 订单主表 10000 条记录（488 unique）→ 需删 9512 条重复

---

## 一、问题概述

4/30 至 5/9 期间，生产 Bitable 订单主表（`tblXXX`）被写入了约 10000 条记录，而实际应该只有 488 条唯一订单。平均每个订单被重复写入约 20 次。

---

## 二、根因：因果链

```
processPendingDrafts（每 2 分钟轮询）
  │
  ├─ batchCreateRecords(orderRecords)
  │   └─ feishuApi("POST", "/batch_create", body)
  │       └─ AbortController 15s 超时
  │
  ├─ 飞书服务端：数据已写入成功
  │  但响应在 >15s 后才到达客户端
  │
  ├─ feishuApi 超时 → catch { return null }
  │  （不区分"网络超时"和"服务端已写入但响应慢"）
  │
  ├─ batchCreateRecords 返回 false
  │   └─ throw new Error("写入订单主表失败")
  │
  ├─ catch 块：retryCount++，草稿文件保留
  │  （未删除草稿 → 下次轮询继续处理）
  │
  └─ 2 分钟后 → 再次 batchCreate → 同一个 orderNo 再次写入
     （当时不存在幂等检查）

循环上限：retryCount >= 10 时转为 .failed 文件
理论最大重复：10 次 × 500 条/批 = 5000 条/订单（实际约 20×）
```

### 涉及的关键代码

| 文件 | 行号 | 代码 | 作用 |
|------|------|------|------|
| `server.js` | 738 | `const okOrder = await batchCreateRecords(TABLES.order, orderRecords);` | 调用飞书批量创建 |
| `lib/feishu.js` | 82 | `timer = setTimeout(() => ac.abort(), 15000);` | AbortController 15s 超时 |
| `lib/feishu.js` | 89 | `catch (e) { return null; }` | 超时→返回 null，**不区分写入成功与否** |
| `server.js` | 739 | `if (!okOrder) throw new Error("写入订单主表失败");` | null → 抛异常 |
| `server.js` | 747-750 | `draft.retryCount++; writeFileSync(fp, ...);` | 草稿保留，下次重试 |
| `server.js` | 648 | `if (draft.retryCount >= 10) { ... }` | 最多 10 次重试 |
| `server.js` | 682-688 | `existCheck = await feishuApi("GET", ...)` | **幂等检查（事后添加）** |

## 三、为什么幂等检查当时不存在

草稿系统（`processPendingDrafts`）上线时的设计假设是 `batchCreateRecords` 的返回值可靠区分成功与失败。但实际上：

- **飞书 API 的写入是异步的**：请求到达飞书服务端后，数据被接受并开始写入，但响应可能因为飞书内部排队、Bitable 负载等原因延迟
- **AbortController 是客户端单方面超时**：不询问服务端"你写完了吗"，而是直接断开连接
- **`feishuApi` 返回 null 不携带错误码**：`batchCreateRecords` 无法判断是"网络断了（数据未写入）"还是"响应慢（数据已写入）"

这两个假设叠加，导致**超时必重试，重试必重复**。

## 四、幂等检查的脆弱点（修复后仍存隐患）

当前代码（server.js:682-688）已加入幂等检查：

```js
const existCheck = await feishuApi("GET",
  `/bitable/v1/apps/${APP_TOKEN}/tables/${TABLES.order}/records?page_size=1&filter=CurrentValue.[订单编号]="${orderNo}"`
).catch(() => null);
if (existCheck?.items?.length > 0) {
  unlinkSync(fp);
  continue;
}
```

**隐患**：此检查依赖同一条 `feishuApi` 链路。如果飞书 API 在高峰期也超时：

```
feishuApi GET 超时 → 返回 null
  → .catch(() => null) 吞掉错误
  → null?.items?.length > 0 → false
  → 幂等检查被绕过（fail-open）
  → 草稿照样写入 → 仍然重复
```

**结论**：幂等检查只在飞书 API 正常响应时生效。当飞书服务本身是瓶颈时，检查形同虚设。

## 五、batch_delete 清理失败分析

### 错误
```
code=1254043 RecordIdNotFound
```
所有批次均报此错误，共删 0 条。

### 格式对比

| 来源 | 格式 | 是否验证可用 |
|------|------|-------------|
| `test_verify_speed.mjs:213` | `{ records: [{"record_id": "rec_xxx"}, ...] }` | ✅ 验证可用 |
| `import_real_skus.js:86` | `{ records: ["rec_xxx", "rec_yyy"] }` | ❓ 未确认 |
| `dedup_orders.mjs`（生产容器） | **未知**（代码不在本地） | ❌ 全部失败 |

### 可能原因

1. **body 格式不匹配**：`dedup_orders.mjs` 可能使用了字符串数组 `["rec_xxx"]` 而非对象数组 `[{"record_id": "rec_xxx"}]`，飞书 API 不识别
2. **record_id 来源问题**：`searchRecords`（POST search API）返回的 `record_id` 格式可能与 `batch_delete`（也是 POST）期望的格式存在差异
3. **权限问题**：token 有读取权限但无删除权限（但错误码是 RecordIdNotFound 而非 AccessDenied，可能性较低）

## 八、建议的加固方案

### 短期（阻止继续重复）
- **幂等检查加超时守卫**：如果 `existCheck` 为 null（API 调用失败），不应继续写入，应 skip 该草稿等下一轮，而非 fail-open 直接写入

### 中期（清理存量）
- 执行 `diag_records.mjs` 诊断 → 确定 `batch_delete` 正确格式 → 修复 `dedup_orders.mjs` → 执行清理

### 长期（防止再生）
- `batchCreateRecords` 失败时应区分"超时（数据可能已写入）"和"API 返回错误码（数据确定未写入）"，超时情况不应立即重试
- 考虑在 `feishuApi` 层引入请求级去重（requestId），飞书 API 本身支持幂等键
