# 三系统架构评估与升级方案

**日期：** 2026-04-12
**背景：** 评估现有销售CRM + 旧订单表 + 供应链三系统架构，是否能支撑10万副/年、700终端、70代理商、峰值500副/天的规模目标，并给出最优架构方案。

---

## 一、现状诊断

### 1.1 当前架构

```
旧订单表（手工录入，~70单/天）
    ↓ 增量同步（日批）
CRM销售飞轮 ←→ 供应链执行系统
（以终端客户ID关联）
```

### 1.2 规模数学

| 维度 | 当前 | 目标 | 倍数 |
|------|------|------|------|
| 日均订单 | 70副 | 400副 | 5.7× |
| 峰值日订单 | 未知 | 500副 | — |
| 年订单量 | ~25,000副 | 100,000副 | 4× |
| 终端客户 | 少量 | 700家 | — |
| 代理商 | 少量 | 70家 | — |
| 销售/培训人员 | 少量 | 20人 | — |

### 1.3 飞书多维表容量上限（硬限制）

| 指标 | 官方上限 | 性能建议上限 |
|------|----------|-------------|
| 单表记录数 | 50,000条 | 20,000条 |

| API速率 | 10次/秒（标准） | — |
| 记录写入 | 批量500条/次 | — |

**关键问题：** 年均10万副订单，旧订单表将在约6-8个月内超过Bitable记录上限（现已~8000条，70/天→年增25,550条，当前表1年内达50,000）。

## 五、具体升级计划（4个阶段）

### Phase 1：订单系统独立化（2026 Q2，4-6周）

**目标：** 解决Bitable上限 + 订单生命周期

- 新建独立订单Base（与旧表分离）
  - 订单表：保留90天活跃 + 季度归档表（每季一张表，无限扩展）
  - 订单状态字段：待确认/已确认/生产中/已发货/已签收/售后
  - 代理商字段：关联代理商表（70家）
- 旧表历史数据迁移至归档表
- 同步脚本改为：新订单Base → 供应链（不再依赖旧表）
- 健康监控：sync_orders.js失败→飞书群通知

**关键设计：归档策略解决Bitable上限**

```
订单_活跃表（滚动90天，上限约45,000条）→ 季度归档表（2026Q1, Q2...）
                                        → 供应链镜像（90天，不变）
```

### Phase 2：代理商订单门户（2026 Q3，6-8周）

**目标：** 解决手工录单瓶颈 + 权限隔离

- 飞书内嵌H5门户（利用飞书机器人 + 网页卡片）
  - 代理商登录（绑定飞书账号）
  - 标准化下单表单（SKU选择、数量、交期要求）
  - 订单状态查询（只看自己的订单）
- 代理商权限隔离：每家代理商只能查看/提交自己的订单
- 订单审核流程：代理商提交 → 销售确认 → 进入生产
- 实现：Node.js轻量后端 + 飞书API（当前tech stack的自然延伸）

> **技术选型说明：** 不用微信小程序（需ICP备案、开发成本高），用飞书H5卡片（代理商已在飞书，成本最低）。

### Phase 3：准实时同步 + 季节性预测（2026 Q4，4-6周）

**目标：** 解决24小时同步延迟 + 寒暑假峰值预案

- 同步频率：日批 → 15分钟增量同步
  - 技术方案：Windows任务计划每15分钟执行sync_orders.js
  - 飞书Webhook：新订单确认时立即推送供应链
- 季节性预备货规则（Rule 10）：
  - 触发：距离寒假/暑假30天 → 自动触发备货建议
  - 参数：可配置节假日日期 + 增量系数（如暑假系数3×）
- 供应链容量预警：当订单速率连续3天 > 300副/天，触发产能预警

### Phase 4：IPO前数据治理（2027-2028）

**目标：** 合规、审计、数据资产化

- 订单数据迁移至云数据库（推荐：腾讯云MySQL + 飞书Bitable同步）
  - 历史全量订单：无上限存储，支持复杂查询
  - 飞书Bitable作为前端展示层，不作为存储主库
- 审计日志：每条订单变更有时间戳+操作人记录
- 数据血缘：订单→生产→发货→回款完整链路
- 考虑引入：金蝶云星空（有飞书官方集成，适合IPO前规范化）
