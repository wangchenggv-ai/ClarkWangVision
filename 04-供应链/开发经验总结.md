## 一、关于飞书 Bitable 的真相

**Bitable 不是数据库。** 以下坑全部踩过：

| 问题 | 表现 | 教训 |
|------|------|------|
| 无事务 | 写订单表成功→写库存失败，数据不一致 | 业务层自己兜底，失败标记人工处理 |
| 无唯一约束 | 订单编号/镜片码唯一性靠代码保证 | 写入前先读去重，batch_create 上限500条 |
| 无自增ID | 所有编号业务层生成（ORD-xxx / 16位HEX） | 用 crypto.randomBytes 而非 Math.random |
| 无 join | 两表关联靠业务层两次查询 | 接受这个限制，不要试图模拟数据库 |
| 字段不存在=静默失败 | 写不存在的字段不报错，读不到才报 | check_schema.js 做字段守卫 |
| 读全表慢 | getStockMap() 读1575行花了10秒 | 加内存缓存，TTL 2分钟 |
| 并发丢失更新 | 两个请求同时读 stock=10，都写9 | withLock() per-key 异步锁 + 锁内 fresh read |

**应对策略（已验证有效）：**
- 内存缓存（`STOCK_TTL=2min`）+ `--fresh` 强制刷新
- withLock per-key 异步锁防并发
- clientRequestId + 10min TTL 防重复提交
- 本地草稿缓冲（下单 50ms 返回，后台30min同步Bitable）

## 二、关于架构决策

### 做得对的

| 决策 | 理由 |
|------|------|
| **三系统分开独立开发**（4.14） | 避免耦合，改一个字段不用等30分钟 |
| **方案B批处理脚本保5.1** | 12天从零到上线，Python+Excel 最轻量路径 |
| **A系统迁云但不接真流量** | 学习Docker/ECS/HTTPS部署，0生产风险 |
| **5.31代码冻结，6月纯测试** | 没有冻结期，bug永远修不完 |
| **Excel批量导入替代网页表单** | 代理商最习惯的方式，开发量最低 |
| **订单系统优先，CRM/供应链下半年** | 80%精力集中在最关键环节 |

### 可以做得更好的

| 决策 | 复盘 |
|------|------|
| **一开始就选Node.js门户 vs 飞书原生工作流** | 花了3月底1周讨论飞书原生方案（混合架构1.0），最后完全没用。早期快速验证可以省时间 |
| **库存并发扣减的复杂度** | 为了实时库存准确做了完整 withLock + 预占/实扣/释放链路，但对于当前业务量（日均~30副），简单扣减+人工对账可能更务实 |
| **规则引擎(automations.js)** | 14条规则写了但 Phase 1 实际没用到多少。应该等业务稳定再写规则 |

## 三、常见坑（剩余3周特别注意）

### 坑1：库存并发（P0风险）
`test_stock_concurrency.mjs` 仍有 6/17 测试失败。如果两个代理商同时下单同一度数，可能 lost update。  
**对策：** W4开发库存基本功能时重点攻克，参考 lib/stock.js 的 withLock 模式。

### 坑2：Chinese 编码在 PowerShell
中文目录名在 PowerShell 中会被乱码截断，可能导致误删。  
**对策：** 部署/文件操作命令先在英文路径验证，不要在生产目录直接跑带中文的 Remove-Item。

### 坑3：Docker BuildKit attestation 不兼容 SWR
华为云 SWR 不支持 BuildKit attestation manifest。  
**对策：** 构建时加 `--provenance=false`，本地 `docker buildx build` 也要注意。

### 坑4：飞书 Token 缓存
`getFeishuToken()` 获取失败时如果仍更新时间戳，会导致7000秒内所有请求用无效token。  
**对策：** 只在获取成功时更新时间戳（已修复，改代码时不要破坏这个逻辑）。

### 坑5：改 CLAUDE.md 里的路径
通用编码原则文件在 `AI配置/CLAUDE_karpathy.md`，不是 `../../CLAUDE_karpathy.md`。  
**对策：** 新增 CLAUDE.md 时统一用 `../../../AI配置/CLAUDE_karpathy.md` 引用。

### 坑6：labels.html 大文件
`labels.html` 体量巨大（~2000行），`order.html` 也有 ~1500行。  
**对策：** 改之前先 Read 定位具体行范围，不要全量读。改前 `grep` 确认变量名唯一（历史坑：重复 const 声明导致白屏）。

## 四、效率技巧

### 部署流程（热更新，不用全量构建）
```bash
scp -i 密钥/key-gaush-lab.pem server.js root@113.44.175.221:/tmp/
ssh -i 密钥/key-gaush-lab.pem root@113.44.175.221 \
  "docker cp /tmp/server.js order-app:/app/server.js && docker restart order-app"
```
需要全量构建时才走 `docker build --provenance=false` → push → pull → up -d。

### 测试策略
- 自动化测试跑核心流程（~130项中 ~100项通过）
- 助理实操验收跑边界情况（异常/并发/错误输入）
- 库存并发测试单独跑（`node test_stock_concurrency.mjs`）
- **测试只在 6月 做，5月31日后不写新测试**（否则开发永远做不完）

### 文档同步
- **写代码前先写业务逻辑**：输入/输出/异常，写不清楚不动手
- **STATE.md 每天更新**：今日完成/明日继续/当前卡点，给下次会话用
- **ARCHITECTURE.md 改字段时同步更新**：字段表是事实源，不同步等于没改
