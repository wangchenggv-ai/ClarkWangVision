# 高视星订单系统 — 混合方案实施计划

**版本:** V1.0
**日期:** 2026-04-17
**决策人:** Clark
**执行人:** Clark (ClaudeCode 辅助)
**核心判断:** 方案 B 保 5.1,方案 A 做长期,单人开发必须聚焦

---

## 一、方案定义

### 方案 B — 本地批处理脚本(保 5.1)

**核心功能:** Excel → 飞书 Bitable + 溯源系统双写,自动生成 QR 码 ZIP

**技术栈:** Python + pandas + requests + python-dotenv

**解决的问题:** 助理每天 5-6 小时手工重复录入 → 30 秒自动完成

**不解决的问题:** 代理商门户、管理页 Web 操作、物流自动化、标签打印自动化

---

### 方案 A — 云上完整系统(做长期)

**核心功能:** 8 步 E2E 完整订单流程(代理商门户 + 助理管理页 + 工厂导出 + 验真)

**技术栈:** Node.js (server.js) + 飞书 Bitable + 华为云 ECS

**当前状态:** 已开发 2 周,测试发现若干 bug,未上线

**目标:** 2026 年 7 月 1 日全量切换,完全替代方案 B

---

## 二、五条铁律(不可违反)

```
1. 4.17-4.30,方案 A 的任何代码零部署到生产
2. 方案 B 和方案 A 用不同代码仓库/分支,不互相合并
3. Phase 1 期间,任何"顺便改一行"的 A 代码冲动全部拒绝
4. 5.1 当天只运行 B,A 完全冷备,禁止切换
5. 5.1 后至少 2 周 B 稳定运行,才启动 A 的灰度
```

**违反任何一条的后果:** 混合方案崩溃,5.1 风险失控。

## 七、Phase 4:灰度期(5.25-6.30)

### 灰度节奏

| 时间 | 范围 | 切换内容 |
|---|---|---|
| 5.25-5.31 | **1 个代理商** | 选合作最好、接受度高的 1 个 |
| 6.1-6.7 | **2-3 个代理商** | 观察稳定性 |
| 6.8-6.14 | **5-8 个代理商** | 扩大范围 |
| 6.15-6.21 | **15 个代理商** | 大规模切换 |
| 6.22-6.30 | **30 个代理商全量** | B 脚本暂停但保留 |

### 每周检查点(全部通过才能扩大)

```
✅ A 写入数据和 B 写入数据字段完全一致
✅ A 的错误率 < B 的错误率
✅ 助理反馈 A 比 B 好用(或至少不差)
✅ 代理商无投诉

❌ 任何一条不满足 → 暂停扩大,回到上一周范围
```

### Fallback 机制

任何阶段出问题,30 分钟内将出问题的代理商切回方案 B 脚本。B 脚本在整个 Phase 4 期间保持可用状态,不下线。
