**版本:** V2.1 (最终确认版)
**日期:** 2026-04-17
**作者:** Clark + Claude
**目标:** 5.1 高峰期(日均 100-200 单)自动化订单录入 + 二维码验真上线

## 一、项目背景

### 1.1 业务问题

高视星在 5.1 销售高峰期预计日均 100-200 单,当前订单处理全靠助理手工录入,瓶颈明确:

- 30 个代理商通过微信群发送标准格式 Excel 订单
- 助理需要在**两个系统**重复录入每一单:
  - **飞书多维表格(Bitable)**:订单管理(客户、地址、物流等 20+ 字段)
  - **溯源管理后台(admin.gaushclear.com)**:验真数据(产品、处方、经销商等 10 个字段)
- 100 单手工录入耗时 **5-6 小时**,且错误率高
- 溯源系统自动生成 QR 码 + ZIP,消费者扫码验真已稳定运行

### 1.2 解决方案

用一个 Python 批处理脚本,**从代理商 Excel 一次性双写飞书 + 溯源系统**,将 5-6 小时的手工录入压缩到约 30 秒。

核心原则:**不替换任何现有系统,只消除重复录入这一个瓶颈**。

### 1.3 不做什么

| 不做的事 | 原因 |
|---|---|
| 不自建验真服务 | 溯源系统已稳定运行,无需重复造轮子 |
| 不部署华为云新服务 | 溯源系统已在高视星自有华为云上运行 |
| 不上线代理商门户 | 5.1 期间微信群发 Excel 足够 |
| 不改造管理页 | 助理用飞书表格 + 溯源后台手工兜底 |
| 不做域名备案 | gaushclear.com 已备案,溯源系统已在线 |

## 二、系统架构

### 2.1 整体架构图

```
代理商微信群发标准 Excel
       ↓
助理收到 → 保存到 inputs/{YYYYMMDD}/
       ↓
双击运行 Python 脚本
       ↓
┌──────────────────────────────────────────────────┐
│  daily_batch.py (Mac 本地)                        │
│  ─────────────────────────                        │
│  1. excel_merger.py   解析 Excel → 合并 → 校验     │
│  2. feishu_client.py  批量写飞书 Bitable            │
│  3. shuang_client.py  逐条写溯源系统 API            │
│  4. 下载溯源系统自动生成的 QR 码 ZIP                 │
│  5. 输出处理报告                                    │
└──────────────────────────────────────────────────┘
       ↓                              ↓
  飞书 Bitable                 溯源系统 (华为云)
  (订单管理)                   (验真 + QR 生成)
       ↓                              ↓
  助理在管理页/CLI               消费者扫码验真
  做后续流程                   shuang.gaushclear.com
  (确认/发货/ZIP导出等)              ↓
                              显示验真结果页面
```

### 2.2 数据流

```
Excel → master.csv(本地真相源)
           ├─→ 飞书 Bitable 订单主表 (tblk9Ch4gk2uQ1zG)
           ├─→ 飞书 Bitable 镜片明细表 (tblC7pve7ObFgIOl)
           └─→ 溯源系统 api.gaushclear.com/api/securityOrderAdd
                  └─→ 自动生成 2 个 barcode(F+15位数字,左右眼各一)
                  └─→ 自动生成 2 张 QR 码图片
                  └─→ 自动打包 ZIP 供下载
```

### 2.3 与原 8 步流程的关系

原 8 步 E2E 流程(详见 ARCHITECTURE.md)完全保留,脚本只替换第 ① 步中的手工录入部分:

| 步骤 | 原方式 | 5.1 方式 | 变化 |
|---|---|---|---|
| ① 订单录入 + 赋码 | 助理手工录入两个系统(5-6 小时) | **脚本自动双写(30 秒)** | **核心改动** |
| ② 确认订单 | 管理页点按钮 | 不变 / 飞书表格手工改 | 无 |
| ③ 发货 | 管理页点按钮 | 不变 / 飞书表格手工改 | 无 |
| ④ 工厂 ZIP 导出 | 管理页导出 | 不变 / CLI 导出 | 无 |
| ⑤ 工厂生产 | 工厂自行 | 不变 | 无 |
| ⑥ 签收 | 管理页点按钮 | 不变 / 飞书表格手工改 | 无 |
| ⑦ 标签打印 | 管理页打印 | 不变 / CLI 打印 | 无 |
| ⑧ 消费者验真 | shuang 系统 | **不变,已稳定** | 无 |

## 三、外部系统接口

### 3.1 溯源系统 API (api.gaushclear.com)

#### 3.1.1 系统概况

| 项目 | 信息 |
|---|---|
| 系统名称 | 溯源管理后台 |
| 管理后台 | https://admin.gaushclear.com |
| API 端点 | https://api.gaushclear.com/api/ |
| 消费者验真页 | https://shuang.gaushclear.com/#/?barcode={code} |
| 部署位置 | 高视星自有华为云 ECS |
| 认证方式 | **无认证(公网裸接口)** |
| 数据格式 | multipart/form-data |
| 编码规则 | F + 15 位数字(如 F415159319625798) |
| 历史数据量 | 7116 条(截至 2026-04-17) |

#### 3.1.2 新增订单接口

```
POST https://api.gaushclear.com/api/securityOrderAdd
Content-Type: multipart/form-data
认证: 无
```

**请求字段:**

| 字段名 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `goods_name` | string | 是 | 产品名称 | `高视星 - Ultra 双效镜片` |
| `barcode_num` | int | 是 | 码量(**固定填 2,左右眼各一码**) | `2` |
| `right_qiujing` | string | 否 | 右眼球镜 SPH | `-3.00` |
| `right_zhujing` | string | 否 | 右眼柱镜 CYL | `-0.75` |
| `righy_zhouwei` | string | 否 | 右眼轴位 AXIS (**注意:原系统拼写为 righy**) | `90` |
| `left_qiujing` | string | 否 | 左眼球镜 SPH | `-2.75` |
| `left_zhujing` | string | 否 | 左眼柱镜 CYL | `0` |
| `left_zhouwei` | string | 否 | 左眼轴位 AXIS | `0` |
| `remark` | string | 否 | 病患备注(存顾客姓名) | `张明辉` |
| `dealer` | string | 否 | 经销商 | `北京视佳` |

**关键业务规则:**
- `barcode_num` 固定填 **2**(一眼一码,一个顾客两个码)
- `righy_zhouwei` 是原系统的拼写错误(应为 right),但 API 字段名不能改
- 所有处方字段类型为 string,不是 number
- 历史数据中 barcode_num 多数为 1 是助理操作错误,正确业务规则为 2

**成功响应:**

```json
{"data": null, "code": 1000, "message": "成功"}
```

- `code: 1000` = 成功
- `data: null` = 不直接返回 barcode,需通过 securityOrderList 获取

**新增后自动触发:**
- 系统自动生成 2 个 barcode(F+15 位数字)
- 自动生成 2 张 QR 码图片(左右眼各一张)
- 自动打包为 ZIP,可在管理后台下载或通过 barcode_url 获取

### 4.2 模块职责

| 模块 | 行数 | 核心逻辑 |
|---|---|---|
| `daily_batch.py` | ~155 | 7 步流程编排,支持 --dry-run / --shuang-only / --feishu-only |
| `excel_merger.py` | ~110 | 列名模糊匹配(6+ 种变体)、同一顾客左右眼合并、必填字段校验 |
| `feishu_client.py` | ~140 | tenant_token → 幂等查询 → batch_create 主表 → batch_create 明细表 |
| `shuang_client.py` | ~150 | 逐条 POST securityOrderAdd(barcode_num=2) → 查列表获取 ZIP → 下载 |
| `config.py` | ~45 | 路径 + 飞书凭证 + 表 ID + 启动校验 |

### 4.3 关键设计

#### 幂等性

- 每次运行先查飞书:「今天有没有 (代理商名称 + 顾客姓名) 相同的记录」
- 已存在则跳过,不重复写入
- 同一天跑 N 次,结果一致
- 溯源系统目前无幂等保护(没有查重接口),需靠飞书侧控制不重复调用

#### 失败隔离

- Excel 解析失败:记录到 warnings,不影响其他文件
- 校验失败:写入 `failed_{date}.csv`,不影响有效订单
- 飞书写入失败:返回失败列表,不影响溯源写入
- 溯源写入失败:单条失败不影响其他条
- ZIP 下载失败:仅打印警告,不阻断流程

#### 可审计性

- `master_{date}.csv` 是每天的本地真相源
- 可随时与飞书 Bitable 和溯源后台数据对照
- 每天一个日期目录,天然归档

## 七、Excel 标准格式

### 7.1 必须包含的列

| 列名 | 必填 | 说明 | 支持的变体 |
|---|---|---|---|
| 顾客姓名 | 是 | 配镜顾客 | 姓名、患者姓名、客户姓名 |
| 眼别 | 是 | 左眼/右眼 | 左右眼、OD/OS |
| 球镜SPH | 是 | 处方球镜 | 球镜、SPH、S |
| 柱镜CYL | 否 | 处方柱镜 | 柱镜、CYL、C |
| 轴位AXIS | 否 | 处方轴位(0-180) | 轴位、轴向、AXIS、A |
| 产品型号 | 是 | SKU 名称 | 型号、SKU、产品 |
| 数量 | 否 | 默认 2 | 数量(片)、片数 |
| 代理商名称 | 是 | 经销商全称 | 代理商、经销商 |
| 终端客户 | 否 | 机构名称 | 客户、门店、机构 |
| 联系人 | 否 | | 收件人 |
| 联系电话 | 否 | | 电话、手机 |
| 收货地址 | 否 | | 地址 |
| 备注 | 否 | | 说明 |

### 7.2 校验规则

| 规则 | 处理方式 |
|---|---|
| 顾客姓名为空 | 标记失败,跳过 |
| 产品型号为空 | 标记失败,跳过 |
| 代理商名称为空 | 标记失败,跳过 |
| AXIS 超出 0-180 | 标记失败,跳过 |
| AXIS 不是数字 | 标记失败,跳过 |
| 同一顾客多行(左右眼) | 自动合并为一行 |

## 十、应急预案

### 10.1 脚本挂了

```
脚本报错
  → 立刻回退手工录入(原来怎么干就怎么干)
  → master.csv 发开发同事排查
  → 修复后重跑(幂等,不会重复)
```

回退成本:30 单以下 1-2 小时,100 单以上需 2-3 人帮忙录入。

### 10.2 飞书 API 挂了

```
  → 先跑 --shuang-only 保证验真数据写入
  → 等飞书恢复后跑 --feishu-only 补写
  → master.csv 是真相源,飞书数据可从 CSV 重建
```

### 10.3 溯源系统 API 挂了

```
  → 先跑 --feishu-only 保证飞书数据写入
  → 助理手工去 admin.gaushclear.com 逐条录入(回退)
  → 等 API 恢复后跑 --shuang-only 补写
```

### 10.4 消费者扫码验真失败

```
  → 检查 shuang.gaushclear.com 是否可达
  → 华为云 ECS 挂了 → 控制台重启
  → Clark 手机保持在线,异常 30 分钟内响应
```

### 10.5 代理商 Excel 格式异常

```
  → failed.csv 记录失败原因
  → 助理修正 Excel 列名后重跑
  → 长期:给代理商发标准 Excel 模板
```
