# 供应链100天计划 — 完成情况交叉分析

> **编制时间：** 2026年5月1日  
> **目的：** 对比"计划写了什么" vs "实际做了什么"，识别偏差与洞见

---

## 一、总体判断：计划与实际已分叉

100天计划（3.20-3.29编制）提出了**三条主线**：
1. 供应链运营改进（Phase 1-3）
2. 飞书供应链系统开发（12张表、9条规则）
3. 5.1订单系统上线

但4月中旬后的实际工作沿着**三条更务实的平行轨道**推进，与计划不完全重合。

### 轨道B：订单系统软件开发（feishu-setup/order-system）← 远超计划的投入

**100天计划原文**对软件系统的描述是"飞书多维表格+AI脚本/9条规则"，是一个**轻量级自动化层**。实际上建成了一个**完整的Web门户**：

| 维度 | 计划预期 | 实际实现 |
|------|---------|---------|
| 架构 | 飞书多维表格原生功能+简单脚本 | Node.js HTTP服务+5个前端页面+华为云Docker部署 |
| 代码量 | ~1,500行脚本 | 6,000+行JS，~130项测试 |
| 存储 | 飞书Bitable为主 | 飞书Bitable + 本地草稿缓冲(Docker volume) |
| 部署 | Mac本地脚本 | 华为云ECS + Docker + lab.gaushclear.com |
| 前端 | 无（操作Bitable） | 5个页面：下单/追踪/管理/控制台/库存 |
| 功能 | 9条规则+仪表盘 | 全状态机(5态+退回)、标签打印、物流回调、CRM同步、库存联动 |
| 测试 | 基本验证 | ~130项测试、E2E模拟、安全边界测试、库存并发测试 |

**现状（截至4.30）：**
- ✅ 订单录入、工厂导出Excel、消费者扫码验真 — **已上线**
- 🔲 库存管理+订单联动 — **50%**（bug清理中）
- 🔲 毛坯库存+两级判断逻辑 — **50%**
- 🔲 打标签+发货 — **50%**（bug测试中）
- 🔲 对账功能 — **未开始**

**洞见：** 计划低估了软件开发的工作量。原计划把"订单系统"当轻量层，实际它成了最大工作项。到6.30的目标已收敛为"功能稳定+做完对账+找接手人"，而非原计划的"暑假高峰日均100副"。

## 四、关键偏差分析

### 偏差1：计划写了"轻量自动化"，实际建了"完整Web系统"

| 计划假设 | 实际发展 | 影响 |
|---------|---------|------|
| 用飞书多维表格原生能力即可 | Bitable API性能瓶颈明显（读库存表10秒+） | 需要本地草稿缓冲、缓存层 |
| 脚本层仅4个核心脚本(1500行) | 订单系统6000+行，含完整前端 | 开发投入超出预期3-4倍 |
| 9条业务规则驱动 | 实际业务规则在server.js中硬编码，automations.js备用 | 规则引擎未成为核心架构 |

### 偏差2：计划低估了"库存管理"的复杂度

计划中库存只是"推拉结合点"的一个策略概念。实际开发中它变成了最复杂的模块：
- 度数级库存（SKU×SPH×CYL = 225行/SKU）
- 两级判断逻辑：成品SKU→毛坯库存
- 库存并发扣减（测试中6/17失败）
- 交期预估（3个档位：2天/7天/10天）

### 偏差3：4.14"三系统独立"决策改变了整个架构方向

原计划隐含三系统统一开发的假设。4.14正式决定：
- 订单系统优先（6.30前）→ 80%精力
- CRM下半年 → 当前仅做数据同步
- 供应链系统下半年 → inventory-system/尚在规划阶段

这意味着计划中的"端到端供应链"（从模具到交付）在6.30前实际只覆盖了"订单到交付"这一段。

### 偏差4：无人员风险应对记录

计划中R5风险（团队AI使用意愿和能力不足）和R2（模芯故障）都有记录，但从W15/W16周报看，**实际卡点是运营层面的**：
- 生产慢 → 不装配超期首因（40%）
- 镜框延误 → W15占比100%，W16降到20%
- 外送装配损伤 → 新增问题
- 客诉积压 → 6例中4例仍在处理中

这些运营细节在计划中几乎没有对应策略。

## 五、几个值得注意的信号

### 1. 装配超期率在上升
```
W14: 4.58% → W15: 5.00%
```
虽然数字仍然不高，但趋势是反的。计划目标→20%以下，当前5%虽然达标，但趋势需要关注。

### 2. 真实交付量离100副/天差距不小
```
W15 (4/13-19) 交付207副 = ~30副/天
计划目标: 100+副/天（暑假高峰）
```
但这是非高峰期数据，暑假才是真正验证。

### 3. 订单系统测试4项失败
```
库存并发测试: 6/17失败 ❌
E2E全流程: 限流429 ❌
部分通过: ~20项 ⚠️
需手动确认: ~20项 ⏸️
```
库存并发是高风险问题——如果两个代理商同时下单导致库存扣错，后果严重。

### 4. 6.30后Clark计划退出开发角色
《系统建设复盘》明确说："630之后Clark = PM+验收者，接手人负责日常维护"。这意味着当前代码质量、文档完备性直接决定了交接成败。
