# CLAUDE_karpathy.md — 通用编码原则

> 本文件适用于所有代码项目。来源：Andrej Karpathy 总结的 LLM 编码常见陷阱与最佳实践。

---

## 1. Think Before Coding

**不假设，不隐藏困惑，暴露权衡。**

实施前：
- 明确陈述你的假设。不确定就问
- 如果存在多种解释，列出来——不要默默选择
- 如果有更简单的方法，说出来。必要时推回需求
- 如果有不清楚的地方，停下来。说明困惑点。提问

## 2. Simplicity First

**解决问题的最少代码。零推测性功能。**

- 不写需求外的功能
- 单次使用的代码不抽象
- 不写没被要求的"灵活性"或"可配置性"
- 不处理不可能场景的错误
- 如果你写了200行但其实50行就够，重写

问自己："资深工程师会说这过度复杂吗？" 如果是，简化。

## 3. Surgical Changes

**只改必须改的。只清理自己的烂摊子。**

编辑现有代码时：
- 不"改进"相邻代码、注释或格式
- 不重构没坏的东西
- 匹配现有风格，即使你会用不同方式
- 如果注意到无关的死代码，提一下——别删

当你的改动产生孤儿时：
- 删除**你的改动**导致不再使用的 import/变量/函数
- 不删除已存在的死代码，除非被要求

检验：每个改动的行都应该直接追溯到用户的请求。

## 4. Goal-Driven Execution

**定义成功标准。循环直到验证通过。**

把任务转化为可验证的目标：
- "加验证" → "为无效输入写测试，然后让测试通过"
- "修bug" → "写一个能复现它的测试，然后让测试通过"
- "重构X" → "确保重构前后测试都通过"

对于多步任务，先列简短计划：
```
1. [步骤] → 验证: [检查点]
2. [步骤] → 验证: [检查点]
3. [步骤] → 验证: [检查点]
```

强成功标准让你能独立循环。弱标准（"让它工作"）需要持续澄清。

---

**这些指南有效的标志：** diff 中不必要的改动更少，因过度复杂导致的重写更少，澄清性问题出现在实施前而非犯错后。
